# 024: MIPComparison 図が stale（016修正前の緩和MIP）で、提案手法が不当に悪く見えていた

## 発生日
2026-07-27（「RR/RV を上げると提案手法の makespan がどんどん悪化する。MIP はあまり悪化しない。ソルバーの解き方が正しいか確認して」との依頼）

## 結論（先に）
- **MIP ソルバー本体は正しい**（時変容量・休暇日を正しく制約。016 修正は現行コードに存在し機能）。
- **表示されていた MIPComparison 図が古かった**のが真因。図は 016 バグ時代の
  **緩和版バックアップ** `results/FUN_MIP_backup_relaxed_20260716/` の値（ms*=109）を
  描いていた PNG で、現行の正しいデータ（ms*=184）に更新されていなかった。
- 修正後: **RV1 の難条件で NSGA(MaxShiftDur) は MIP 最適に完全一致**（j309_1: 184=184, 457=457）。
  → 「提案手法が makespan でどんどん悪化」は **too-good な緩和MIPと比べていた錯覚**が主因。

## 決定的検証（016 の相互検証プロトコル、新ターゲット MIPVERIFY）
`main_MIP_Verify.cpp`＝`MIPVERIFY` を作成。RR/RV 指定で MIP makespan 最小解を解き、得た
開始時刻を capacity_t に対し feasibility 検証（先行/資源/休暇日貫通）。
- **j309_1 RR050_RV1**: fresh MIP makespan=**184（最適性証明済み）**, 先行違反0/資源違反0/休暇日貫通0。
  horizon T=597, 休暇スロット=172。→ 完全に実行可能で正しい。
- **j309_1 RR000_RV0**: fresh MIP=**83**（図と一致＝harness は正しい値を再現）。

## 別件の要注意（新発見・未解決）: コスト軸の MaxShiftDur が MIP より安い
- 修正後図で MaxShiftDur min-cost（例 307,383）< MIP min-cost（413,926）。**厳密解より安い＝あり得ない**。
- 原因候補: ①**MaxShiftDur のコスト表不一致（017 で既知・「再実行必要」のまま未解決）** ②コスト表は
  T=165 までしか定義されていないのに RV1 の horizon は 597 → t≥165 に遅らせたジョブのコストが
  未定義/クランプで安くなり、遅延型の MaxShiftDur が exploit している疑い。
- → **コスト軸の手法間比較は MaxShiftDur を共通コスト表で再実行するまで無効**。makespan 軸は有効。

## 追加検証（2026-07-27）: 「MIP が悪すぎる/提案手法が制約違反では?」への回答
新ターゲット `MSVERIFY`（`main_MaxShift_Verify.cpp`）: 提案手法(MaxShift P1/MaxShiftDur)を実走し、
最終前線の**全解**を capacity_t で feasibility 検証。「報告 ms*（違反解込み最小）」vs「実行可能のみ ms*」。

| 条件 | encoding | 前線 | 報告ms* | 実行可能ms* | 違反解数 | maxPrec |
|---|---|---|---|---|---|---|
| RR050_RV1 | MaxShift P1 | 316 | 184 | **184** | **0** | 0 |
| RR050_RV1 | MaxShiftDur | 367 | 184 | **184** | **0** | 0 |
| RR075_RV1 | MaxShift P1 | 406 | 457 | **457** | **264** | 5 |
| RR075_RV1 | MaxShiftDur | 298 | 457 | **457** | 21 | 3 |

結論（2方向とも確定）:
1. **提案手法の makespan 最適値は phantom ではない**。RR050_RV1/RR075_RV1 とも 実行可能ms*=報告ms*=
   MIP最適（184, 457）。NSGA は独立に MIP 最適へ feasible に到達＝**両者一致で 184/457 は真の最適**。
2. **ただし高 RR/RV では前線に制約違反 phantom が混入**（RR075_RV1 で MaxShift 264/406 個, prec違反≤5）。
   022 の serial 末尾フォールバック（[est,T) に置けないジョブを後方探索で est 前に置く）が高競合で
   多発するため。今回は最小makespan解は無事だったが、**別条件では phantom が ms* を汚す危険**あり。
   → **全 NSGA 前線は plot/報告前に実行可能解のみへフィルタすべき**（PSGS で実装済みの方式を横展開）。
3. **MIP は「悪すぎ」ではない**。総作業量 Σd=165 に対し makespan 184(RV1)/457(RR075_RV1) は、
   ①休暇日(RV)で全資源が14日毎に停止＋ジョブが休暇日を跨げない、②RR=0.75 で容量が公称25%まで
   **時刻ごとに i.i.d. 変動** → 長ジョブが連続高容量スロットを得られず右に押される、が原因で
   **強制アイドルが大量発生**するため。難インスタンスの正しい最適値であり、ソルバー欠陥ではない。

## 教訓
- **手法比較で片方が異常に強い/弱いときは、まず「見ている図が現行データか」を疑う**
  （016「同じ問題を解いているか疑え」の系）。データ修正後に **PNG を再生成し忘れる**と、
  古い結論を引きずる。図の legend の数値と現行 FUN ファイルの値を突き合わせる。
- backup ディレクトリ（`*_backup_relaxed_*`）は**可視化から物理的に隔離**すべきだった。
- コスト表の horizon（165）< スケジュール horizon（597, RV1）は独立した設計欠陥。要修正。
