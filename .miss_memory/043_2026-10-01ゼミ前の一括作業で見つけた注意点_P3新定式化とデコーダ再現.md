## 1. MaxShiftDur デコーダの Python 再現（分析専用）は C++ と完全一致する
- `msd_decoder.py`（作業用。analysis/ext1001 の分析で使用）は RCPSP_Problem_MaxShiftDur::evaluate を
  そのまま写した: EST → t_mak → [t_mak, min(T-d, t_mak+win)] で strict '<'（最早優先）の最安。
- 検証: 拡張 MIP の j309_1 全6条件・133解で、「開始時刻順の活動リスト + 窓幅 w=s*-t_mak」で復号すると
  **実活動の開始時刻とコストが 133/133 一致**。
- 最初は 124/133 に見えたが、ずれは**終端ダミー活動（所要時間0）だけ**だった（下の2）。
  → ダミーを含めて開始時刻を比較しないこと。

## 2. MIP 前線の「メイクスパン」は実スケジュールの終了時刻より大きいことがある
- j309_1（拡張）で 9/133 点。終端ダミーの開始時刻が ε 上限（例: 89）のままで、実作業は 87 で終わっている。
- tighten（同コストで工期最小化）はコストが前の点より下がったときしか走らないため、残ることがある。
- 影響: MIP 基準線のメイクスパンがわずかに不利（大きめ）に記録される箇所がある。比較時に留意。

## 3. NSGAMaxShiftDurCpp のログの「beta=0」は表示だけのバグ（実際は 0.5）
- verifyDegenerate（main_NSGAII_RCPSP_MaxShiftDur.cpp:631 付近）が `cout << fixed << setprecision(0)` を
  戻さないため、直後のヘッダで beta=0.5 が「0」と表示される。計算は beta=0.5（main の既定値）。
- ログの beta 表示を根拠に判断しないこと。

## 4. NSGA は実行ごとに結果が変わる（シード固定なし）

- 手法比較では「同じ設定を2回走らせた差（ノイズ）」を必ず基準に置くこと。

## 5. 旧 P3（単位活動の鎖、036）は基準線として使えない → 時刻別実行の新定式化 P3Slot
- 旧 P3 の j309_1 RR000_RV0: (124, 354,134) gap 4.8%、(165, 328,015) gap 3.5%。
  同じ工期で P1（351,371）より高い＝緩和問題なのに P1 より悪い暫定解しか出ていなかった。
- 新ツール `P3Slot`（main_P3Slot.cpp）: y[j][t]=時刻 t に実行、f[j][t]=t の時点で完了済み、
  y[s][t] <= f[i][t] で先行関係、ε 制約は「t>=ε の y を作らない」。変数は P1 の約2倍。
- 試運転（j309_1 RR000_RV0, ε 3点, 120s）: 83→384,416（P1 388,259）、122→346,538（P1 351,371）、
  最小コスト 328,205（P1 334,939）。**すべて P1 以下＝緩和関係と整合**。ただし最適性は未証明（gap 2〜3.5%）。
- 拡張コスト表専用（--cost-dir=costs が指定されたら停止）、出力は results/EXT_COST/FUN_MIP_P3SLOT/ のみ。

## 6. 新しい実行ファイルを追加するとき
- NMake ジェネレータでは CMakeLists.txt に add_executable を足した後、`cmake -S .. -B cmake-build-release`
  で再構成しないと「ビルド方法が指定されていません（U1073）」になる。
- 実行中の exe は上書きビルドできない。バッチが使っている exe を変えたいときは別名ターゲットを作る
  （例: rho 実験用 NSGAMaxShiftDurRPCpp。ソースは同じ main_NSGAII_RCPSP_MaxShiftDur.cpp）。

## 7. --rho-power（窓幅 win = round(rho^k * eff)）を追加。既定 1.0 で従来と同一
- RCPSP_Problem_MaxShiftDur::setRhoPower / main の --rho-power。k=1 のとき pow は呼ばれない。
- 実験は必ず --tag を付けて出力名を分ける（例: _rp3）。結果は ゼミ原稿 と analysis/ext1001/rho_summary.json。

## 8. 結果: ρ べき乗マッピング（前回の「案A」）は不採用（2026-10-01 確定）
- j30 全48インスタンス・276条件、拡張コスト表、各1回実行。共通正規化 HV の差（k=1 の平均との差）:
  - ノイズ（k=1 同士）: +0.0005（SE 0.0008）、改善94/悪化84 → 偏りなし
  - k=3: −0.0056（SE 0.0009）、66/210 → 有意に悪化

  - 評価回数1/4: k=1 で −0.0272（2/274）。1/4 同士で k=3 − k=1 = −0.0219（24/252）

## 9. 結果: P3Slot（新定式化）j309_1 RR000_RV0, ε 10点, 120s/解

## 10. P3Slot には P1 解の初期解（--warm）が必須（休暇ありの条件）
- 初期解なしだと j309_1 RR000_RV1（T=597）で最小メイクスパンの解が 120 秒で 147 までしか下がらず、
  P1 の 100 より悪い（緩和なのに矛盾）。前線もメイクスパン146以上しか出なかった。
- `--warm=<P1 の SCHED_MIP ファイル>` で各 ε に「ms<=ε の P1 最良解」（工期最小化では cost 上限以下の最小 ms）を
  Gurobi の Start に与える。P1 の解は中断しないだけの P3 の解なので必ず実行可能。
- 結果: RR000_RV1 は 89〜587 の前線、最小コスト 288,305（P1 324,660 より 11% 安い）、P1 より悪い点 0。
  RR000_RV0 は最小コスト 326,015（P1 334,939）。全点時間切れ（gap 2〜4%）。
