# 046: 実行キューの改行コード（CRLF）でタグに CR が入り、結果ファイルが1つも保存されなかった

## 発生日
2026-10-16（複数回実行の確認。tools/ext1014/queue_20261016*.txt を xargs -L 1 で並列実行）

## 何が起きたか
- キューファイルを Windows の Python でテキストモード書き込みしたため、各行が CRLF になった。
- `xargs -L 1 bash run_one.sh` で読むと、行の最後の引数に `\r` が付く。
  - base の行は最後の引数がタグ（`t1016_base_r1\r`）→ **出力ファイル名に CR が入り、Windows では作れないので
    ofstream が黙って失敗**。FUN/SCHED/TRACE が1つも保存されないのに、終了コードは 0、進捗表示も正常。
  - isrgp / isrg の行は最後の引数が数値（`30\r`, `0.1\r`）で、stoi/stod が CR を無視するので無事だった。
- ログファイル名だけは MSYS が CR を私用文字に置き換えて作れていたので、「ログはあるのに結果が無い」状態になった。
- 結果: j30 の base 240 実行と j120 の base 数十実行をやり直し（約1時間のロス）。

## 教訓
- キューや引数リストを Python で書くときは `open(..., "w", newline="\n")`、読む側は `sed -i 's/\r$//'` で正規化する。
- 長い一括実行は、最初の数件が終わった時点で **出力ファイルが期待どおりの名前で存在するか** を手法ごとに確認する
  （終了コード 0 と進捗ログだけでは保存の失敗は分からない）。
- `run_one.sh` 側でも最後に出力ファイルの有無を確認して表示するとよい（未対応）。
- 名前に CR を含むファイルを bash の `$'*\r*'` で find しようとすると、環境によっては全ファイルに一致する。
  直すときは Python の os.walk で文字を確かめてから行う。
