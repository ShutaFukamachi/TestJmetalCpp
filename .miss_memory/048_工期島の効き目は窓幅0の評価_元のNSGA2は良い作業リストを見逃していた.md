# 048: 工期島の効き目は「窓幅0で評価すること」。元の NSGA-II は良い作業リストを生んでも窓幅で見逃していた

## 発生日
2026-10-23（10/21 ゼミ指摘「工期島も本体も操作は同じなのに、なぜ工期島ではメイクスパンの良い解が出るのか」）

## 追加したもの（すべて既定 OFF）
- NSGAII: msSelProb/msSelTop（親をメイクスパン上位から選ぶ）、costSelProb/costSelTop（コスト上位から）、
  zeroWinProb（子の窓幅を0にする）、msMateProb/msMatePatience/msMateFilter（1集団の中の工期島）、
  traceChildren（trace に child 行: 親と子の内訳、子の作業リストを窓幅0で復号した工期）。
- ランナー: --ms-sel --ms-sel-top --cost-sel --cost-sel-top --zero-win --ms-mate --ms-mate-patience --ms-mate-filter --trace-children
- 事前登録: tools/ext1023/PREREG_20261023.md

## 分かったこと
- 元の NSGA-II（j30 全条件、--trace-children）:
  - 親のうち工期最小から5%以内は 20%（工期側の親が選ばれていないわけではない）。
  - 子が集団の最良メイクスパンを実際に更新: 子100万体あたり 15.2
  - 子の作業リスト（窓幅0）が「集団の最良工期」と「集団の作業リストの最良」の両方より短い: 100万体あたり 672.9（44倍）
  → **良い作業リストを持つ子は生まれているが、親から受け継いだ窓幅で工期が伸び、工期の改善として認識されずに失われる。**
  - 最初の集計（集団の最良工期とだけ比べた 475 倍）は、最良個体自身の窓幅で隠れた作業リストのコピーを数えて過大だった。
    厳密版（作業リストの最良とも比べる）を必ず使う。
- 1集団での切り分け（j30 × 3回、事前登録の判定は「4手法とも不十分」）:
  - 窓幅0の子（zw）だけで工期端 226.7・探索で到達 82%（工期島 224.0・79% 以上）→ 工期島の効き目は (B) 窓幅0の評価。
  - メイクスパンで親を選ぶだけ（ms）は 209.0・58%。(A) は補助。
  - ただし zw は HV が工期島より −0.0020。「窓幅0が集団に広がる」仮説は棄却（窓幅すべて0の個体は100体中約1体）。
    残る説明は「工期側が解けた後も評価の17%を使い続ける予算のむだ」。
- 計算時間（他の計算なし、1インスタンス6条件）: 手法による差は小さい（評価回数が同じため）。
  j30 約20〜28秒、j60 74〜94秒、j90 160〜180秒、j120 217〜246秒。

## 運用の注意
- Git Bash の heredoc（<<'PY'）で `"\\n"` を含む置換をすると一致しないことがあった。バックスラッシュを含むパッチは
  Write ツールでスクリプトファイルを作ってから実行する。
- NSGAII.cpp は CRLF と LF が混ざっている（追記した部分が LF）。置換は両方の改行で試す。
- 並列は4（16スレッド／20コア）にした。CPU に余裕を残す。

## 最終結果（2026-10-24 00:40、事前登録 tools/ext1023/PREREG_20261023.md）
- 1集団版で事前登録の基準 (a)(b)(c) を満たしたのは「工期側の両親→窓幅0、改善のみ受入、止めない」（matef0）だけ。
- しかし最終設定どうし（優先規則初期解・ブロック窓込み）では、1集団版は中間部 10.51%（2集団 9.94%）、
  j120 HV −0.0058（120条件中108で悪化）→ **2集団を標準のまま**。
- 工期島と同じ止め方（子の最良の停滞で止める、--ms-mate-stall-child）にすると前線は戻るが工期端 217.2 に落ちる。
- 理由: 工期島は約30世代で止まり予算の約1.4%しか使わないが、その間「集団の最良に届かない途中段階の窓幅0の作業リスト」を
  20本ためて改良し続けられる。1集団ではそれらがコストで負けて捨てられる。
- 作業数ごと（PSPLIB 最良既知との差、現在 → 最終設定）: j30 0.88→0.31%、j60 2.77→1.04%、j90 3.89→1.64%、j120 11.50→5.07%。
  HV は作業数が大きいほど改善幅が大きい（+0.0066, +0.0124, +0.0160, +0.0192）。
- SchedObj（従来法）は j90・j120 でも全条件で MaxShiftDur に負ける（j120 最良既知との差 18.79%）。
- 短時間: 評価回数 1/4 でも工期端は現在の手法より良いが、前線全体は今の評価回数近くが要る。
- 時間ブロック窓変異（--time-block-win、開始時刻が近い作業の窓幅をまとめて動かす）を採用（j30 中間部 8.98→8.54%、
  j120 HV +0.0136）。
- SchedObj の NSGAEncCpp は1インスタンス約24分（2つのエンコーディング×6条件）。j120 は長い。
- 2時間制限のある待ち合わせジョブに「前のかたまりの終了待ち＋長いかたまり」をつなぐと超えることがある。合計時間を見積もってから
  つなぐ（超えそうなら止めて、終了通知を受けてから起動する）。
- 最終設定を prtbw3（--pr-init 0.5 --island 20 --regen 0.1 --island-patience 30 --time-block-win 0.3）に置き換えた（事前登録で採用）。
  作業数ごとの HV の改善は 10/21 の最終設定のおよそ2倍（j120 +0.0189 → +0.0365、360/360）。工期端はほぼ同じ。
  j120 では計算時間が +23%（現在の手法比、同じ時間帯に交互測定）。
