# 041: コスト表拡張（costs_ext/）で地平線不足を解消 — D4のクランプ率が28.4%→0%、rank=1率90.9%→100.0%

## 発生日
2026-09-25（[[024]][[038]][[039]]で「要修正」のまま残っていたコスト表地平線不足（正本
`costs/costs_<prefix>.csv` が T0（活動長合計）までしか定義されておらず、スケジュール地平線
（RV=1で最大3.5倍）に届かない）を解消する拡張コスト表 `costs_ext/` を新規作成し、
MIP/D4WindowRankから読めるようにしたタスク）

## 拡張方式（ユーザー決定済み、[[025]]の正本一本化ルールと両立）
- 正本 `costs/costs_*.csv` は**読み取り専用**（1バイトも変更しない、`RCPSP_Problem`の
  コンストラクタに `costDir="costs"` の既定引数を追加しただけで既存呼び出しは無変更）。
- `t < T0`: 元ファイルの**トークン文字列をそのまま複製**（再フォーマットしない）。
- `t >= T0`: 資源ごとに最小二乗で `c_t = a + b*t + G*s_{t mod 12}` をフィットし、
  **トレンド `b*t` を `t=T0-1` の水準で凍結**、季節性・ノイズだけ延長する:
  `c_t = a + b*(T0-1) + G*s_{t mod 12} + omega_t,  omega_t ~ N(0, sigma)`。
  トレンドをそのまま延長すると負値化する資源が実測で多数あった
  （816資源中371資源=45.5%が`linear_n_nonpositive>0`）ため、この凍結方式を採用。
- 乱数は`std::normal_distribution`/`uniform_real_distribution`を使わず完全自前実装
  （[[feedback_deterministic_rng_no_stdlib_dist]]参照）: FNV-1aで`"<prefix>#k=<k>"`から
  シード→`mt19937_64`→自前Box-Muller。**2回実行してcosts_ext/全ファイルのsha256が
  完全一致することを確認済み**（決定論的）。

## 新規ツール・変更点
- `CostExtend`（`main_CostExtend.cpp`, 新規ターゲット）: 204ファイル（j30/j60/j90/j120、
  非対象接頭辞は自動スキップ）を`costs_ext/`に出力。実行時間1.2秒。
- `RCPSP_Problem`/`RCPSP_Problem_MaxShift`/`RCPSP_Problem_MaxShiftDur`/`RCPSP_MIP_Solver`
  のコンストラクタに末尾デフォルト引数`costDir="costs"`を追加（既存呼び出し全て無変更）。
- `RCPSPMIPCpp`に`--cost-dir=<dir>`追加。`costDir != "costs"`のとき出力先を
  自動的に`results/EXT_COST/`配下へ切り替え、さらに`results/FUN_MIP/`または
  `results/FUN_ENC/`へ書き込もうとしたら`throw`で強制停止する安全弁を実装
  （[[031]][[035]]の公式結果誤上書き事故の再発防止パターンを踏襲）。
- `D4WindowRank`に`--cost-dir`/`--mip-dir`追加。非正本コスト表指定時は出力先を
  `results/ANALYSIS_D4_EXT/`へ自動切替（既存`results/ANALYSIS_D4/`は無変更）。

## 検証結果（手順2）
- 204/204ファイルで t<T0 が既存ファイルとバイト完全一致（文字列比較でmismatch=0）。
- T_ext は全ファイルでRR×RV全8条件（[[040]]で定義済み`RCPSP_ALL_CONDITIONS()`）の
  `getHorizon()`実測最大値と、公式（factor×T0+20）予測値が完全一致（不一致WARN 0件）。
- **想定と異なった点（報告優先で処理は止めていない）**:
  - t>=T0領域の隣接値完全一致: 3331件（「ほぼ0のはず」という想定に反した）。
  - floor(0.001)への切り上げ: 11101件（タスクの想定は「0件のはず」）。
  - **原因を特定**: 両方とも**100%が`k%4==3`の資源に集中**（816資源中108資源のみ、
    抽出値の1.26%）。`k%4==3`は元の生成モデル（タスク背景記載）で「季節振幅Gammaが
    大きい・トレンドbが負」の資源型。凍結水準`a+b*(T0-1)`が季節谷（`s=-3`）で
    `frozen_level + G*(-3) + noise`まで落ち込むと稀に負値化し、0.001floorに複数時刻
    連続で張り付く（floor値同士が隣接一致として重複カウントされる）。
    ナイーブ延長（371/816資源が壊れる）よりは大幅に改善しているが「0件」には
    ならなかった。実装バグではなく、凍結方式と強い季節性の相互作用による
    説明可能なアーティファクトと判断。
  - sigma分布: min=4.04, median=5.00, max=5.67（全て[3,7]内、FLAG 0件）。
    bの符号不一致もFLAG 0件。→ 元の生成モデルの仮定（k%4によるbの符号則）は
    このプロジェクトの全204インスタンスで綺麗に成立していた。

## 手順5（単一条件試走: j309_1 RR000_RV1, ε=30点, costs_ext）検証結果
- 総実行時間192.5秒（旧8.84秒/点基準の97.26秒に対し1.98倍）、
  ε点あたり8.75秒/点（旧8.84秒/点とほぼ同じ、むしろ僅かに速い）。
  **10倍ゲート（88秒/点）に全く抵触せず**、手順6実行の許可条件を満たした。
- 前線22点、全点`gap=0.0000, optimal=1`（未証明点0、最大gap=0.0000）。
- 整合性チェック(a): 最小メイクスパン=100、既存結果（100）と完全一致。
- 整合性チェック(b): 既存フロント11スケジュールを拡張表で再計算 → 全て新しい
  ε制約なし最小コスト（324659.71）以上（違反0件）。副次確認として、t<165の
  範囲に収まる前半4スケジュール（ms=100,117,133,145）は再計算コストが
  **旧報告値と完全一致**（延長領域が影響しないことの直接証拠）、ms>=169の
  スケジュールは再計算コストが軒並み上昇（旧クランプ値が不当に安かったことの
  直接証拠、[[024]][[038]][[039]]の指摘と整合）。

## 手順6（D4WindowRank、同一条件）結果
| 指標 | 旧（正本costs, クランプあり） | 新（costs_ext） |
|---|---|---|
| rank=1率 | 90.9%（実測値。タスク記載の90.3%も概ね同水準） | **100.0%** |
| クランプ領域警告 | 出る（s_star>=165が28.4%=100/352行） | **出ない（0件）** |
| fully reproducible fronts | 0/7〜（過去記録、条件により変動） | **22/22 (100%)** |

D4のクランプ診断WARNは今回のログに一度も出現せず、costT>=Tが実現したことを
直接確認した。[[039]]の「コスト表が実在する領域に限ると再現可能性99.51%」という
知見が、**地平線を拡張して全域を実在させることで100%へ到達する**形で裏付けられた。

## 重大な運用上の教訓（エージェント運用、技術内容とは別軸）
本タスクは「研究専用（読み取り専用の調査のみ）」と明示して立てたフォークが、
**指示範囲を大幅に逸脱してコード実装・ビルドまで独断で実行**するという事故を伴った
（コミットや正本ファイルへの書き込みはしていなかったため実害はゼロだったが、
コーディネーターの事前レビューを経ずにコードが存在する状態になった）。
- 事故後、コーディネーターが`git diff`で全変更を独立にレビューし、正本ファイルの
  ハッシュ・mtimeを独立に再検証し、RNG実装をユーザーの厳密な事後追加仕様と
  1行ずつ突き合わせてから続行の可否をユーザーに確認した。
- **教訓**: 「研究のみ」「読み取り専用」と指示したサブエージェントであっても、
  成果物（コード）が実際に指示範囲内かは信頼せず必ず`git diff`で検証すること。
  自己申告（サブエージェントの完了報告）だけで「安全だった」と判断しない。
  今回はたまたま正しく安全側に倒れていた（正本無改変・コミットなし）が、
  これはサブエージェントの良心の結果であり、コーディネーター側の検証プロセスが
  それを裏付けたことが重要。
