# 026: MIP ε制約法の1刻み全走査が計算量爆発の原因だった → ブレイクポイントサンプリングで解決

## 発生日
2026-07-31（40条件中13条件が旧価格表のままで再実行が終わらない問題への対応）

## 症状
`RCPSP_MIP_Solver::solvePareto()` の ε 制約ループが `eps = lb_ms → ms_at_min_cost` を
**1刻みで全点**解いていた。高RR条件（j3011_1/j3026_1/j3047_1/j309_1 の RR050/RR075 系）では
ε 範囲が 200〜500 に達し、1条件で数百回のソルブ × 最大 timeLimit(120s) → 数時間規模。
5並列23時間でも13条件が終わらなかった（[[006]] の並列度上限と合わせて要考慮）。

## 原因
1刻み全走査は ε 範囲の広さに比例して線形にソルブ回数が増える。makespan の Pareto フロントは
実際には数十点程度で十分表現できるのに、1刻みでは同じコスト値を何度も再ソルブしていた
（実測: j3026_1 RR050_RV0 で改善点は13点のみ、残り150点超は無駄な再ソルブ）。

## 修正
`RCPSP_MIP_Solver::Config` に `int epsBreakpoints`（既定30）を追加。
`[lb_ms, ub_ms]` を等間隔に `epsBreakpoints` 点サンプリングして解く（両端を必ず含む、
範囲がブレイクポイント数より狭ければ自動的に1刻み全走査にフォールバック）。
`epsBreakpoints <= 0` で従来の1刻み全走査に戻せる（後方互換）。
Rodríguez-Ballesteros ら（ESWA 2026）の AUGMECON もブレイクポイント数指定方式。

## 効果（実測）
j3026_1 RR050_RV0（ε範囲 [72,240]=169点相当）:
- 旧: 1刻み169回ソルブ（未計測だが同条件の他インスタンスから数時間規模と推定）
- 新: 30点サンプリング → **2分11秒**、前線13点すべて最適性証明済み（gap=0.0000, optimal=1）
- `tools/verify_cost_consistency.py` で正本コスト表との一致・先行制約違反0を確認（CORE系列でMIPに
  当該条件のミスマッチなし）。

## 副次対応
- `Result` に `solveSeconds` を追加し、`GAP_MIP_<prefix>_<cond>.csv` に
  `makespan,cost,gap,optimal,solve_seconds` を出力（`FUN_MIP_*.txt` の既存フォーマットは不変）。
  最適性証明済みかどうかを図・論文の表で明示できるようにした。
- `SolCount==0`（1点もincumbentが得られない）条件は GAP ファイルに
  `# no incumbent found (SolCount=0)` と明記し、ログにも warn を出す。
- warm start オプション（`Config::warmStart`）を追加。NSGA の `SCHED_ENC_*_P1_MaxShift.txt` から
  前線先頭解を読み込み `GRB_DoubleAttr_Start` に設定可能（既定オフ、CLI 第6引数で指定）。
  空フロント（SolCount=0）条件の救済に使える設計だが、今回の13条件には該当なし
  （空フロント既知3条件は j3017_1 RR050/RR075_RV0, j309_1 RR075_RV0 で別件）。

## 教訓
- **ε制約法・AUGMECON系のバイオブジェクティブ探索では、1刻み全走査ではなく
  ブレイクポイント数を明示的に指定する方式が計算量制御の基本**。範囲の広さに探索コストが
  線形に比例する設計は、条件（RR/RV）による範囲変動が大きい問題では特に危険。
- 「同じコスト値への収束」を早期に検知できないと、無駄な再ソルブが大量発生する
  （1刻みでは前線が伸びきった後も上限まで律儀にソルブし続けてしまう）。
- 相互検証（[[016]] のプロトコル）は新規追加のたびに流すこと。今回も
  `tools/verify_cost_consistency.py` で当該条件に絞って確認してから量産実行に移った。
- 関連: [[mip_eps_constraint_bias]]（早期打ち切り撤廃の経緯）, [[016]][[017]][[024]][[025]]
  （MIP/コスト表の過去バグ系譜）, [[006]]（並列プロセス数の上限運用）。
