# 037: P2 MIP を NSGA 側定義（活動・資源ごとのγ判定）に一致させる「活動ごと圧縮」定式化へ再実装

## 発生日
2026-09-07（[[036]] で P3 の計算量爆発を報告した後、指導教員確認を経て P2 の定義一致タスクとして着手。
**実装のみで停止する指示のため、ビルド・実行はしていない**）

## 問題（[[036]] で発見済みの副次的事実の本格対応）
MIP側の旧P2実装（`--split-mode P2`、[[036]]作成時点の実装）は「全資源が同時に容量0になる
休暇日」だけを時間軸から除去する**全体圧縮**だった。これは NSGA 側 `RCPSP_Problem_Splitting::
simulateP2/executeP2` の本来の定義
```
γ_jkt = 0 ⟺ capacityAtTime(k,t) < demand[j][k]  → 中断してよい（活動・資源ごとの判定）
```
の特殊ケースに過ぎない。実測乖離: RR000_RV1で0%、RR025_RV1で0〜3.5%、**RR050_RV1で44%**。

## 解決方針: 活動ごとに独立した実行可能時刻集合 A_j
```
A_j = { t : すべての資源 k で capacityAtTime(k,t) >= demand[j][k] }
```
活動 j は A_j 上で「連続した d_j 要素」を占める変数 x[j][i]（i は A_j 内の開始位置）を使う。
これにより NSGA の γ 判定と完全一致する。

## なぜ既存の RCPSP_MIP_Solver::buildModel を流用できなかったか（P3・旧P2との違い）
- **P3（単位分割）**: 実時間軸そのまま・単位ジョブが1スロット連続実行 → 既存の x[j][t]（t=実時刻）
  モデルにそのまま乗る。**新規制約は本当に不要だった**（[[036]]参照、計算量爆発はしたが定式化は妥当）。
- **旧P2（全体圧縮）**: 全ジョブが**同一の共有圧縮軸**を使うため、圧縮後 index をそのまま実時刻の
  代わりに使う「x[j][t']」として既存 buildModel にそのまま渡せた（コスト表だけ別途remap）。
- **新P2（活動ごと圧縮）**: **ジョブごとに異なる軸**（A_j が活動ごとに違う）を持つため、
  「x[j][t]の t が全ジョブ共通の実時刻」という buildModel の前提が崩れる。资源制約・先行制約を
  「A_j内の位置→実時刻」の対応表を使って組み直す必要があり、**新規の制約構築コードが必須**だった。
  → `RCPSP_MIP_Solver.cpp` は一切変更せず、`src/problems/RCPSP_MIP_SolverP2Activity.{h,cpp}`
    に完全独立実装した（P1のリスクをゼロにするため）。

## 実装のポイント
- 資源制約: A_j の構築自体が「demand[j][k] > capacityAtTime(k,t) となる t を除外」しているため、
  旧 P1 が必要としていた「容量0スロットでUB=0を明示的に張る」workaround（[[016]]）は**不要**
  （そもそも該当する x[j][i] 自体が存在しない）。地味だが定式化がシンプルになった副産物。
- 先行制約・目的関数: 実開始 `A_j[i]`・実完了 `A_j[i+d-1]+1` は **A_j という定数配列を係数**にした
  線形式で書けるため、Gurobi的には通常のスケジューリングMIPと変わらない複雑さ。
- ダミー活動（d=0）: 資源を消費しないため `A_j = [0..T-1]`（恒等写像）として扱い、実質 P1 と
  同じ「実時刻インデックス」に自然に帰着する（特別扱いを最小化）。
- コスト: 圧縮していない実時間軸をそのまま使うため、旧P2で必要だった「コスト表の一時オーバーライド」
  （`overrideGlobalCostTable`/`restoreCanonicalCostTable`）は**不要**。正本コスト表を直接参照する
  だけで済む（[[025]]の「正本一本化」方針にとってよりシンプルな経路）。
- 実行不能の事前検出: `|A_j| < d_j` となる活動が1つでもあれば、Gurobiを呼ぶ前に
  `computeP2ActivityScale()`でログに明記して打ち切る（[[026]]の"no incumbent found"を
  Gurobi任せにせず、意味のある診断を先に出す）。

## 判断: 旧実装（全体圧縮）は削除せず `--split-mode P2-legacy` として残した
- 理由: 「削除せず別モードとして残すか、置き換えたことを記録するか、どちらでもよい」という
  タスク指示に対し、**将来の比較検証（新旧の乖離をインスタンス横断で定量化する等）に使える
  可能性がある**ため物理削除はせず、CLIから両方到達可能にした。
- `--split-mode P2` = 新（活動ごと圧縮、NSGA定義に一致）
- `--split-mode P2-legacy` = 旧（全体圧縮、休暇日のみの特殊ケース）
- 出力先を分離: `results/FUN_MIP_P2/` と `results/FUN_MIP_P2-legacy/`（P1公式結果には
  どちらも一切書き込まない、[[031]][[035]]の事故を踏まえた設計）。

## 教訓
- **「既存の定式化を流用できる」という判断は、変換が全ジョブで単一の共有軸に帰着するか
  どうかで決まる**。単位分割（P3）や単一圧縮軸（旧P2）は t を実時刻のまま扱えるので流用できるが、
  ジョブごとに異なる軸（新P2）は流用できない。表面的に似た「時間軸を変換する」タスクでも、
  軸が「共有」か「個別」かで実装の複雑さが質的に変わる。
- **NSGA側とMIP側で同じ名前（P2）のモデルを別々に実装する場合、定義の一致を最初に数式レベルで
  確認すべきだった**（[[036]]で44%という無視できない乖離が出てから気づいた）。次に同種の
  MIP定式化タスクを受けたら、既存のNSGA実装のコメント・コードを最初に読み合わせること。

  [[036]]（P3の計算量爆発、本タスクの発端）。
