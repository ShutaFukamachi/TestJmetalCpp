# 036: P3（単位分割）MIP は production timeLimit(120s) では解けない — 計算量爆発を実測、ステップ1で停止

## 発生日
2026-09-03（P2/P3 MIP 定式化タスクのステップ1検証）

## やったこと
- 指導教員の指摘（「新しい定式化を書かずに既存P1用MIPを流用できる」）に基づき、
  P3（任意中断）を「所要時間dの活動をduration=1の単位活動d個に鎖状先行制約で分解し、
  既存の`RCPSP_MIP_Solver`にそのまま渡す」方式で実装。
  - `RCPSP_Problem::replaceInstanceForMIPTransform()`（新規）で instance をメモリ上で
    差し替えるだけ。`RCPSP_MIP_Solver::buildModel()`等は一切変更していない。
  - 容量プロファイル・コスト表（正本 `costs/costs_<prefix>.csv`）は元インスタンスの
    ものをそのまま使用（[[025]]の一本化ルールに準拠、書き換えなし）。
  - `main_MIP_RCPSP.cpp`に`--split-mode P1|P2|P3`を追加（既定P1で現行動作不変）。
  - 出力は`results/FUN_MIP_P3/`に分離（[[031]][[035]]の公式ファイル誤上書き事故を
    再発させないため。今回確認: `results/FUN_MIP/j309_1/`のmtimeは変化なし）。

## ステップ1実測結果（j309_1, RR000_RV0, epsBreakpoints=3, timeLimit=120s/solve）
| 指標 | P1 | P3(単位分割) | 倍率 |
|---|---|---|---|
| ジョブ数 | 32 | 167 | 5.22x |
| horizon T | 165 | 165（不変、正しい） | 1x |
| 概算バイナリ変数数(nJobs×T上限) | ≈5,280 | ≈27,555 | 5.2x |
| 求解時間/点 | ≈0.5s | **420.2s（実測平均）** | **≈840x** |

- 3つのε点のうち、**ε=83（P3自身のmin-makespan lb）ですら「infeasible」**と報告された。
  ただし `solveMakespan()` は同じモデルで ms=83 の incumbent を実際に見つけている
  （＝ms=83 は構造的に存在するはずの解）。これは「真の実行不能」ではなく、
  独立な cold-start ソルブ（`solveCost(83)`）が 120s 以内に **1つも incumbent を
  見つけられなかった**（SolCount=0）ことを「infeasible」として扱っている
  （[[026]]で既知の "no incumbent found" パターンと同型）。
- 残り2点（ε=124, ε=165）は解を得たが、**両方とも `solve_seconds=120.01`
  （timeLimitに完全に張り付き）、`optimal=0`（gap 3.5〜4.8%、証明されていない）**。
  つまり「解けた」ように見える2点も厳密解ではなく、単なる打ち切りincumbent。

## 結論・判断
- タスク側の事前基準「求解時間がP1の10倍を超えたら一旦報告」に対し、**実測は約840倍**。
  桁が2つ以上違う、明確な閾値超過。
- 5.2倍の変数増加が、線形ではなく**求解困難性の質的な変化**（秒未満→タイムアウト張り付き）
  を引き起こしている。時刻インデックス型定式化はバイナリ変数数に対して非線形に難化する
  典型例（[[026]]の「5並列23時間停滞」事故と同種のリスク）。
- **ここでステップ2（P1/P3フロント比較）・ステップ3（条件拡大）・第2部P2の実行には
  進まず、ユーザーに報告して相談する**（タスク側の明示的指示に従う）。P2のコードは
  実装済みだが未実行（同じ理由で計算量リスクを先に確認すべきため）。

## 副次的な発見（要ユーザー確認）
- NSGA側 `RCPSP_Problem_Splitting` の既存P2定義（`γ_jkt=0 ⟺ capacityAtTime(k,t) <
  demand[j][k]`、ジョブ・資源ごとの個別しきい値判定）と、本タスクのMIP側P2定義
  （全資源が同時に容量0になる「休暇日」のみ除去する時間軸圧縮）は**別の緩和モデル**。
  後者はP1にそのまま流用できる利点があるが、前者とは数学的に同一問題ではない。
  「MIP P2 vs NSGA P2」を同一ラベルで比較する場合は、この違いを踏まえる必要がある。

## 次の一手（ユーザー判断待ち、実行はしていない）
1. timeLimitを大幅に伸ばす（例: 600〜1800s/solve）— ただし1インスタンス1条件で
   数十分〜数時間かかる計算量になり、実験規模を通せない可能性が高い。
2. Gurobi側のチューニング（`MIPFocus=1`実行可能性優先、`Heuristics`強化、
   対称性のある単位分割ジョブへの対称性破壊制約の追加検討）。
3. 単位分割の粒度を緩める（duration=1ではなく、たとえば「元の活動を2〜3分割」程度に
   とどめる中間的な定式化）— ただし「既存P1をそのまま流用」というタスクの前提から外れる。
4. RR000_RV0（最も軽い条件）でこの結果のため、他条件（RR/RV上昇でTがさらに伸びる）は
   確実にさらに悪化する。P3のMIP厳密解アプローチ自体の実用性を再検討する必要がある。

## 教訓
- **「既存定式化の流用」は制約・変数の「型」を増やさなくても、変数の「個数」の増加だけで
  実務的に解けなくなることがある**。理論的に正しい定式化でも、規模見積り（ジョブ数×T）
  だけでなく実測の求解時間を必ずステップ1で確認してから展開すべき（タスクの事前ゲートは
  正しい安全策だった）。
- **「infeasible」という報告は、時間制限付きMIPでは「真に実行不能」ではなく「制限時間内に
  incumbentを1つも見つけられなかった」ことを意味しうる**（[[026]]の教訓の再確認）。
  gapや`optimal`フラグ・`solve_seconds`がtimeLimitに張り付いているかを必ず確認すること。
- 関連: [[016]][[017]][[024]][[025]]（MIP/コスト表の過去バグ系譜）、[[026]]（ブレイク
  ポイント方式・no incumbent found パターン）、[[031]][[035]]（公式結果ファイル誤上書き
  事故、今回は出力先分離で再発なしを確認）。
