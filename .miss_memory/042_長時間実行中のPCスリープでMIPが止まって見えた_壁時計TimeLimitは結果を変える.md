# 042: 長時間実行中に PC がスリープし MIP が「止まって見えた」— 壁時計の TimeLimit はスリープで結果そのものを変える

## 発生日
2026-09-25（拡張コスト表 `costs_ext/` での試運転 `run_48_comparison_ext.sh 9 9`、j309_1 の MIP）

## 症状
- j309_1 RR000_RV0 の MIP が ε=131 のまま 13:10 から約1時間40分ログが進まなかった。
  TimeLimit=120s なのに1回の求解が終わらないように見えた。
- 当初の推定は2つとも誤り:
  - 「Gurobi が制限時間を守らずに走り続けている」（こちらの推定。プロセスを強制終了してしまった）
  - 「同一モデルでも Gurobi の実行時間がばらつく」（CLion 側の推定）

## 真因（Windows イベントログで確定）
- 13:10:30 Kernel-Power 42「システムがスリープ状態になります」
- 14:49:57 Power-Troubleshooter 1「システムは低電力状態から再開しました」
- ログが止まった時刻とスリープ開始が**秒単位で一致**。CPU 時間の積算もこの間ほぼゼロだった
  （ps の CPU 秒 ÷ 経過秒が約1.3コア＝稼働していたのは前後の約50分だけ）。
- 復帰時点で壁時計の TimeLimit を過ぎていたため、ε=131 は gap 0.0148 で打ち切られた
  （旧公式結果では同じ点が 33 秒で最適解）。
- 強制終了したのは、復帰して ε=142 まで進んだ**直後**だった（止める必要はなかった）。

## 教訓
1. **Gurobi の TimeLimit は壁時計**。スリープを挟むと、その求解は「打ち切り」になり、
   前線の値そのもの（どの点が最適性未証明になるか、gap）が変わる。時間の記録だけの問題ではない。
2. 「止まっている」と判断する前に、(a) Windows イベントログのスリープ/復帰、
   (b) プロセスの CPU 時間の増え方、を確認する。ログが進まないだけでは判断しない。
3. ファイルにリダイレクトした標準出力はバッファされ、進捗が見えなくなる（問題2）。
4. CLion を閉じても、`nohup`/バックグラウンドで起動した実行は止まらない（試運転はそのまま完走した）。

## 対策（2026-09-25 実装済み）
- `src/util/KeepAwake.h`: `SetThreadExecutionState(ES_CONTINUOUS|ES_SYSTEM_REQUIRED)` を
  RCPSPMIPCpp / NSGAEncCpp / NSGAMaxShiftDurCpp の main 冒頭で呼ぶ。起動ログに `[KEEPAWAKE] enabled`。
  電源設定は変更しない。蓋閉じ・手動スリープは防げない。
- 3つの main で標準出力を行ごとに書き出す（setvbuf + unitbuf）。
- `tools/run_48_comparison_ext.sh`: MIP 終了ごとに GAP の solve_seconds>180 を
  `.run48_ext_logs/suspect.csv` に記録。
- 旧公式 `results/FUN_MIP/` は solve_seconds>180 が0件（最大 120.30 秒）で、スリープの影響なし。

## 再実行の結果（2026-09-25 15:19〜18:10、スリープ0回）
- j309_1 の6条件を再計算。RR000_RV1 は試運転（22点）と完全一致。
- RR000_RV0（地平線165で拡張部分を使わない＝旧公式とモデル同一）は、両方で最適性が証明された
  10点がすべて旧公式と一致。値が違ったのは時間切れの3点のみ（壁時計の制限なので想定どおり）。
- 付属分析 MaxShiftSensitivityAnalyzer の --cost-dir 渡し漏れも修正済み
  （2026-10-01 のバッチで拡張表を読むことを確認）。
