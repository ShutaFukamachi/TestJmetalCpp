# 031: A1 priority-rule シードの本番A/B検証 — 効果はインスタンス依存、一律改善ではない

## 発見日
2026-08-12（工期gap改善Step1: A1を本番ランナーで有効化しA/B比較するタスク）

## 実装
`NSGAEncCpp`（`main_NSGAII_RCPSP_EncodingComparison.cpp`）と `NSGAMaxShiftDurCpp`
（`main_NSGAII_RCPSP_MaxShiftDur.cpp`）に `--a1` CLIフラグを追加し、
`NSGAII::a1PrioritySeed` を切り替え可能にした（既定OFF、変更なし）。
- `runStrategies`（EncodingComparison）/ `runStrategiesP1`（MaxShiftDur）に
  `bool a1PrioritySeed` 引数を追加し、async lambda内で
  `algo->setInputParameter("a1PrioritySeed", &a1Flag)` を呼ぶだけの最小変更。
- SchedObj: `createPriorityRuleSolution` は `RCPSP_Problem_MaxShift` にのみ存在し、
  基底 `RCPSP_Problem`（SchedObjが使うクラス）には無い。NSGAII.cpp側は
  `dynamic_cast<RCPSP_Problem_MaxShift*>(problem_)` で判定するため、SchedObjでは
  自動的に no-op になる（クラッシュや誤動作はしない）。**Step1の対象外**、確認のみ。
- MaxShiftDur: `RCPSP_Problem_MaxShiftDur : public RCPSP_Problem_MaxShift` なので
  dynamic_castは成功し、`createPriorityRuleSolution`（活動リスト部分）は正しく効く。
  **ただし** `NSGAII.cpp` 内の「半分はUniform[0,halfT]でコスト探索多様化」の`halfT`は
  `msProb->getEffectiveHalfT()` を **`RCPSP_Problem_MaxShift*` 型のポインタ経由**で
  呼んでいる。`getEffectiveHalfT()` は非virtualで、`RCPSP_Problem_MaxShiftDur`側は
  シャドーイング（`R`を返す別定義）しているため、**静的型で解決され基底版
  （halfT=T/8〜T/2）が呼ばれてしまい、本来使うべき`R`（例1000）ではなく
  遥かに狭い範囲でrhoキーがサンプリングされる**。活動リスト自体（A1の主眼）は
  正しく効くため致命的ではないが、コスト探索多様化の効果は設計意図より狭い。
  **今回は修正せず（Step1のスコープ外）、既知の制限として記録**。

## 作業中の重大な手順ミス（データ整合性の教訓）
`NSGAMaxShiftDurCpp` は `results/FUN_ENC/<prefix>/` に**直接書き込む**設計
（`NSGAEncCpp` はcwdに書いてから移動する設計と異なる）。8インスタンスのA1=ON実験で、
この違いを見落として `--a1` 付きで実行した結果、**公式A1=OFFベースラインの
MaxShiftDurファイルを8インスタンス分上書きしてしまった**（P1_SchedObj/P1_MaxShiftは
cwd経由でFUN_ENC_a1on/に退避済みだったため無事）。
- 対処: 上書き後のA1=ONデータを`results/FUN_ENC_a1on/`にコピー退避 → 該当8インスタンスで
  `NSGAMaxShiftDurCpp`（`--a1`無し）を再実行しA1=OFF公式データを復元。
  48インスタンス中40インスタンスは無傷（diff 0件を確認）、復元した8インスタンスは
  NSGA-IIの確率的性質上、元の数値と完全一致はしないが同一分布のサンプルとして有効
  （`analysis/gap48/gap_summary.csv`の該当行はこのタスク内で正しく再計算・更新済み）。
- **教訓**: 出力パスが「cwdに書いてmv」と「対象ディレクトリに直接書く」でランナーごとに
  異なる場合、A/B実験で退避漏れが起きやすい。**次回以降、新しいバイナリの出力先を
  cwd経由か直接書き込みか、実行前に必ず確認する**（`grep -n "results/FUN_ENC" main_*.cpp`
  等で書き込み先を先に洗い出す）。

### SchedObj（A1の効果を受けないはずの対照群）
cost_gap 1.739%→1.740%（Δ0.001pt）, ms_gap 18.265%→17.393%（Δ-0.87pt）。
**この-0.87ptはA1と無関係な実行間ノイズ**であり、8インスタンス規模でのNSGA-IIの
run-to-run分散の目安になる。MaxShift側の改善（-0.87pt）やMaxShiftDurの悪化（+0.34pt）
は、この**ノイズ床とほぼ同じ大きさ**であり、8インスタンスだけでは統計的に有意な
改善と言い切れない。

## 結論・示唆
1. **A1は一律improvementではない**。j309_1では明確に効くが、最悪インスタンスの
   j3034_1では逆に悪化する。工期gapが最も大きいインスタンスにこそ効いてほしいのに
   逆効果、という点が特に問題。
2. **コストを犠牲にする副作用（FBI型の破綻）は無い** — 安全性の観点では導入障害はない。
3. 8インスタンスという規模はSchedObj対照群のノイズ床と同程度の効果しか検出できておらず、
   **48インスタンス全体で確定させる判断は時期尚早**。
4. j3034_1のような「A1で悪化する」インスタンスの特徴（活動数は全て30、資源逼迫度や
   先行密度で層別できるか）を調べてから展開するのが妥当。
5. **既定は引き続きOFFのまま**（今回の変更で導入したものではなく、A/B確認用の
   スイッチとして--a1を追加しただけ）。

## 次のステップ判断
task説明にある「Step2候補」の判定基準（A1で十分縮むなら既定ON、縮まないならA2）に照らすと、
**「一部縮むが一部悪化」という中間的な結果**のため、以下のいずれかを推奨:
- (a) より多いインスタンス数（16〜24程度）でA1のみを再検証し、ノイズ床を超える有意差か
  確認してから判断する
- (b) A2（単目的makespanシード）を先に試し、「2目的の選択圧不足」と
  「A1のpriority-ruleの質」のどちらが効くかを切り分ける
- (c) j3034_1でA1がなぜ悪化するのかを個別調査する（LFT/MTS/GRPWのどの規則が
  悪さをしているか、seed注入で他の初期集団の多様性を奪っていないか）
