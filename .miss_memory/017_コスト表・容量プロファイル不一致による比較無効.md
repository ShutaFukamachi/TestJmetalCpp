# 017: ランナー間のコスト表・容量プロファイル不一致により手法間比較が無効だった

## 発生日
2026-07-16

## 症状
MIPComparison 図で MaxShift が MIP / MaxShiftDur に大差で負けて見えた。
しかし共通のコスト表で全スケジュールを再評価すると、差はほぼ消滅した。

## 検証結果（決定的証拠）

### 1. コスト表の不一致
共通 CSV（costs/{inst}/costs_{inst}.csv == costs/{inst}/costs.csv 確認済み）で
SCHED ファイルの開始時刻からコストを再計算:

| 系列 (j3026_1 RR050_RV0) | 報告値 | 再計算値 | 一致 |
|---|---|---|---|
| P1_MaxShift | 321010 | 321010 | YES |
| MaxShiftDur | 268214 | 320488 | **NO** |
| MIP (旧) | 265870 | 318372 | **NO** |

→ MaxShiftDur と旧 MIP は**別のランダムコスト表**で動いていた。
  「MaxShiftDur のコストが 16% 良い」は完全なアーティファクト
  （共通表では 320488 vs 321010 でほぼ同等）。

### 2. 旧 FUN ファイル（results/FUN/ の拡張子なしファイル）は完全に無効
非決定論的シード時代（001_capacity_t 参照）の産物で、capacity_t もコスト表も現行と異なる。
例: j3047_1 RR050_RV0 の ms*: 旧 FUN=88、現行 P1_MaxShift=67（=MIP 最適値）。

### 3. 共通コスト表での公平な再評価（RV0 条件）
- MaxShift の makespan は MIP 最適値にほぼ全条件で一致（67=67, 103=103, 118=118, 83=83）
- コストも -1%〜+6% の範囲（MIP スケジュールに勝つケースもある）

## 教訓
- **グローバル状態（COST_TABLE, capacity_t）に依存する手法間比較では、
  全手法が同一のテーブルを使ったことを毎回検証すること。**
- 検証方法: SCHED ファイルの開始時刻から目的値を再計算し、報告値と突き合わせる
  （このスクリプトをリポジトリに常設すべき）。
- 「報告値が良い/悪い」だけで古いファイルを採用しない。まず同一問題かを確認。
- コスト表は RCPSP_Problem コンストラクタが costs/{prefix}/costs.csv をロードするが、
  ファイルが無い場合は**黙って新しいランダム表を生成して上書きする**。
  この暗黙のフォールバックが不一致の温床（明示的エラーにすべき）。

## 対応
- MIP は 016 のバグ修正込みで再実行中（正しい CSV をロードすることを確認済み）
- MaxShiftDur も再実行が必要（現状の数値は比較に使用不可）
- 可視化は旧 results/FUN/ を参照しないこと（FUN_ENC の現行ファイルのみ使用）
