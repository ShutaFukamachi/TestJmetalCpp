# 009: メモリリーク蓄積によるOOMでCLionごとクラッシュ

## 発生日
2026-06-10

## バグの概要
`numStrategiesSchedObj=4, numStrategiesMaxShift=4` に設定したところ、
プログラム実行中に CLion 自体がクラッシュした。
`hs_err_pid*.log` に「insufficient memory for the Java Runtime Environment」と記録されており、
C++ プロセスのメモリリークがシステム RAM を使い切り、CLion の JVM まで道連れにしたことが確認された。

## 根本原因

### リーク1: Algorithm::~Algorithm() が空デストラクタ
`addOperator()` で `new` した Operator（crossover, mutation, selection の3つ）が、
`delete algo` を呼んでも解放されなかった。

```cpp
// 修正前
Algorithm::~Algorithm() {}  // operators_ の Operator* を解放しない
```

スケール: 1インスタンスあたり 4ストラテジー × 3オペレータ = 12個のリーク
20インスタンス実行で 240個の Operator オブジェクトがリーク。

### リーク2: NSGAII.cpp の CrowdingDistanceComparator が毎世代リーク
```cpp
// 修正前（バグあり）
front->sort(new CrowdingDistanceComparator());  // delete されない
```

`SolutionSet::sort()` は渡された Comparator を delete しない設計。
1 NSGAII 実行で 約500世代 × 実行回数分の Comparator が蓄積。
4ストラテジー対応により 4倍に増幅 → OOM の主因。

## 修正内容

### 修正1: Algorithm::~Algorithm() でオペレータを解放
```cpp
Algorithm::~Algorithm() {
    for (auto& pair : operators_) {
        delete pair.second;
    }
    operators_.clear();
}
```

### 修正2: スタック変数の CrowdingDistanceComparator を使用
```cpp
// 修正後
CrowdingDistanceComparator cdcLocal;
front->sort(&cdcLocal);
```

## 診断方法
CLion がクラッシュした場合、プロジェクトルートに `hs_err_pid*.log` が生成される。
このファイルに「insufficient memory」が含まれていれば OOM が原因。

## 教訓
- `SolutionSet::sort()` は Comparator を delete しない。`new` で渡してはいけない
- `Algorithm::~Algorithm()` は必ず operators_ を delete する実装にすること
- numStrategies を増やすとメモリリークも倍増する点に注意
- ストラテジー数を増やして実験する際は、まずメモリリークがないかコードを確認すること
