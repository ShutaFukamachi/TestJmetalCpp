# 028: j30 48インスタンス比較 — gap分布は中央値1%未満、改善優先度は低いと判断

## 発見日
2026-08-10（j30X_1, X=1..48 全件で MIP/MaxShiftDur/MaxShift/SchedObj を比較する48インスタンス
タスクの完了時）

## 背景
5インスタンスでの予備調査で「MaxShiftDur は厳密解に対し平均 +0.67%」という結果が出ていたが、
これが統計的に意味のある差なのか、48インスタンスの分布で確認する必要があった。

## 実行結果サマリ
- 48インスタンス × 6条件(RR∈{0,0.25,0.5}×RV∈{off,on}) × 4系列(MIP/MaxShiftDur/MaxShift/SchedObj)
  を欠損なく完走。
- 所要時間: 試走(3インスタンス)実測562秒から3.5〜4時間と見積もったが、実測は88456秒(≈24.6時間)。
  ログの chunk 間 elapsed 差から、実計算時間というよりマシンのスリープ/セッション跨ぎ（会話中に
  日付が複数回進んでいた）による停止時間を含んでいる可能性が高い。次回は `date +%s` ベースの
  elapsed ではなく実プロセス時間で見積もる方が正確。

## gap分布（matched-makespan gap = (c_NSGA-c_MIP)/c_MIP, ms<=mでc_NSGA最小）
`analysis/gap48/gap_distribution_summary.csv` より（条件ごと・手法ごと、gap_mean の分布）:

| 手法 | 中央値レンジ | 平均レンジ | gap>1%のインスタンス数(/41-48) |
|---|---|---|---|
| MaxShiftDur | 0.33%〜0.55% | 0.38%〜0.65% | 1〜7 |
| MaxShift    | 0.35%〜0.72% | 0.45%〜0.77% | 4〜9 |
| SchedObj    | 1.14%〜1.51% | 1.26%〜1.57% | 26〜36 |

- **MaxShiftDur が最も MIP に近く、RR が上がるほど gap がわずかに拡大する**（RR000: 平均0.38-0.43% →
  RR050: 平均0.47-0.65%）が、最大値でも 1.68%（RR050_RV0）に留まる。
- **SchedObj は MaxShiftDur/MaxShift よりも系統的に約3倍悪い**（中央値が常に1%超）。
- Top-10（MaxShiftDur, 6条件平均）: j309_1(1.36%), j3047_1(1.10%), j3013_1(1.03%) が上位。
  2%を超えるインスタンスは無し。

## 所見: 改善の優先度は低い
中央値が RR000/RR025 でほぼ0.5%未満、RR050でも0.55%程度、最大でも1.7%未満に収まっており、
task 側の判定基準（中央値<0.5%なら優先度低）にほぼ合致する。RR依存の緩やかな悪化傾向はあるが
急激ではない。**MaxShiftDur エンコーディングのアルゴリズム改善は現時点で優先度低いと判断。**
一方 SchedObj は明確に劣るため、比較対象としては残すが「改善すべき手法」ではなく「MaxShiftDur の
優位性を示す対照群」として扱うのが妥当。

## 整合検証で見つかった2種類の異常とその扱い
`tools/verify_cost_consistency.py --prefix-regex '^j30[0-9]+_1$'` を実行すると CORE 系列で
FAIL になるが、原因は以下の2つで、いずれもバグではなく既知の要因。**集計は点単位でフィルタして
実施**（`tools/gap48_analysis.py` 参照、条件全体は除外せず該当解のみ除外）。

### ① 真の実行不能（12件の instance×condition、集計から除外）
MIP ログに `Infeasible (makespan solve)` が出ており、NSGA側も全個体がペナルティ 1e9 になる
（=両手法が独立に「解なし」と結論、矛盾なし）。RR050 に集中。
対象: j3017_1(RR050_RV0), j3020_1(RR025_RV0/RR025_RV1/RR050_RV0/RR050_RV1),
j3021_1(RR050_RV0), j3033_1(RR050_RV1), j3036_1(RR025_RV1/RR050_RV0),
j3037_1(RR050_RV0/RR050_RV1), j3038_1(RR050_RV1)。

### ② [[022]] 由来の先行制約違反 phantom（点単位で除外、条件は残す）
serial デコーダの末尾フォールバックにより、稀に先行制約違反の解が front に混入する
（既知・未修正）。ほとんどのインスタンスは 1〜15点/600〜1900点（<2%）だが、
**j309_1 RR050_RV0 の SchedObj は 85.6%、j3021_1 RR050_RV1 は 63〜80%、j3038_1 RR050_RV0 は
43〜71%** など一部で極端に高いフィルタ率が出た。これらの行は gap_mean が少数点から算出されて
いるため、数値は参考程度に扱うこと（`analysis/gap48/gap_summary.csv` の
nsga_n_prec_filtered/nsga_n_total で確認可能）。

### ③ NSGA が MIP に対し「支配」に見えるケース（3件、バグではない）
例: j301_1 RR000_RV1 MaxShift で ms=88 の NSGA 解(cost=102496)が MIP の ms=89 点(cost=103198,
optimal=1証明済み)より良く見える。**原因は MIP の ε-breakpoint サンプリング(epsBreakpoints=30)
が疎で ms=88 を評価していないため**であり、NSGA が真の最適を超えたわけではない。matched-makespan
gap の定義上こうしたケースは gap を若干過小評価する方向にしか働かないため、結論には影響しない。

### ④ NSGA が実行不能から全く解を出せなかったケース（2件、MIP は解あり）
j3025_1 RR050_RV0, j3033_1 RR050_RV0 は MIP が feasible な前線を持つのに NSGA 側が全個体
ペナルティ 1e9（フロント0件）。他の①とは異なり **NSGA固有の探索失敗**であり、①(両者不能)とは
区別して報告する価値がある（本タスクはアルゴリズム変更をしない測定タスクのため対処はしていない）。

## 教訓
- **48インスタンス規模の比較では、5インスタンス予備調査の平均値（+0.67%）は概ね妥当**だったが、
  RR依存の傾向や外れインスタンス(j309_1等)は多インスタンスでないと見えない。
- **matched-makespan gap 計算は「点単位フィルタ、条件は残す」方針が実務的**。条件ごと除外
  （1件でも不一致があれば除外）は 022 バグがほぼ全インスタンスに薄く存在するため非現実的。
- **verify_cost_consistency.py の FAIL は自動的に「データが壊れている」を意味しない**。
  cost>=1e9 は意図的な実行不能ペナルティであり、MIP ログの "Infeasible" と突き合わせて
  初めて「バグでない」と判断できる。次回同種の検証をする際はまずこの照合を行うこと。
- 関連: [[022]]（先行制約違反 phantom の根本原因）, [[026]][[027]]（MIP ε-breakpoint 方式）。
